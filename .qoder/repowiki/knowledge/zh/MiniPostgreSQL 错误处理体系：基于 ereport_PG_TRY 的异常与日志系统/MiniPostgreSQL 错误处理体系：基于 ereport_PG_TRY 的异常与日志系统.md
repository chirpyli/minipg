## 1. 采用的系统与架构

MiniPostgreSQL（裁剪版 PostgreSQL 14.23）完整继承了 PostgreSQL 的错误处理体系，核心围绕 `ereport`/`elog`、`PG_TRY/PATCH/RE_THROW` 以及 SQLSTATE 编码构建，采用**结构化异常 + 多级别日志**的双轨模式：

- **异常传播**：通过 `setjmp/longjmp` 实现的 `PG_TRY / PG_CATCH / PG_FINALLY / PG_RE_THROW` 宏栈（定义于 `src/include/utils/elog.h`），配合全局 `sigjmp_buf *PG_exception_stack` 和 `ErrorContextCallback *error_context_stack` 链，实现跨模块、可嵌套的异常捕获与重抛。
- **错误报告**：新式 API `ereport(elevel, errcode(...), errmsg(...), errdetail(...), errhint(...), errcontext(...))` 组合字段构造错误对象；旧式 `elog(elevel, fmt, ...)` 作为便捷包装。
- **错误级别**：`DEBUG5..DEBUG1` → `LOG` / `LOG_SERVER_ONLY` → `INFO` → `NOTICE` → `WARNING` / `WARNING_CLIENT_ONLY` → `ERROR` → `FATAL` → `PANIC`，由 `elog.h` 中常量定义，其中 `ERROR` 中止事务并返回已知状态，`FATAL` 终止进程，`PANIC` 拉垮所有后端进程。
- **SQLSTATE 编码**：通过 `MAKE_SQLSTATE(ch1,ch2,...)` 将 5 字符 SQLSTATE 压缩为整型，分类查询用 `ERRCODE_TO_CATEGORY`，具体码表在 `src/backend/utils/errcodes.h`（自动生成自 `errcodes.txt`），覆盖成功完成、警告、连接异常、数据异常、完整性约束违反、事务状态异常等全部标准类别。

## 3. 架构与约定

### 3.1 错误构造与传播流程
1. 任意模块调用 `ereport(ERROR|FATAL|PANIC, errcode(...), errmsg(...), ...)`。
2. `ereport` 展开为 `errstart(elevel, domain)` → 填充各字段 → `errfinish(__FILE__, __LINE__, func)` → 若 elevel ≥ ERROR 则通过 `pg_re_throw()` 触发 `siglongjmp` 到最近的 `PG_CATCH` 块。
3. 未捕获的 `ERROR` 沿调用栈向上传播至 TCOP 顶层（`src/backend/tcop/postgres.c`），由 `EmitErrorReport` 输出到服务端日志并通过 libpq 以 `ErrorResponse` 报文发给客户端；`FATAL`/`PANIC` 直接走 `proc_exit` 或 `AbortTransaction` 路径。
4. 捕获方在 `PG_CATCH` 中可选择 `PG_RE_THROW` 上抛、记录日志后恢复、或执行子事务中止。

### 3.2 上下文与回溯
- `errcontext`/`errcontext_msg` 允许回调函数附加上下文信息（如“正在扫描索引 xxx”），形成 `GetErrorContextStack()` 可查的上下文链。
- `errbacktrace()` 借助 `execinfo.h` 生成调用栈。
- `errposition`/`internalerrposition`/`internalerrquery` 标注 SQL 游标位置与内部查询文本。

### 3.3 递归错误保护
`elog.c` 维护 `errordata[ERRORDATA_STACK_SIZE=5]` 小栈与 `recursion_depth`，当错误处理本身再次报错（最常见是 OOM）时，重置 `ErrorContext` 到空状态以最小化依赖，避免无限递归导致 PANIC。

### 3.4 日志输出与可插拔
- GUC 参数控制：`Log_error_verbosity`（TERSE/DEFAULT/VERBOSE）、`Log_line_prefix`、`Log_destination`（stderr/syslog/csvlog/eventlog）、`syslog_sequence_numbers`、`syslog_split_messages`。
- `emit_log_hook_type emit_log_hook` 允许预加载库拦截错误消息（例如审计插件）。
- `write_stderr`/`write_stderr_signal_safe` 提供信号安全的前 elog 阶段输出。

### 3.5 断言策略
`Assert()` 失败不走 elog，直接 `write_stderr("TRAP: ...")` + backtrace + `abort()`。可选 `SLEEP_ON_ASSERT` 让调试器能 attach。这是为了在基础设施可能损坏时仍能输出诊断。

## 4. 约定与约束

| 约定 | 说明 | 依据 |
|---|---|---|
| 必须搭配 `errcode` + `errmsg` 使用 `ereport` | 注释明确“error level 必需，且需要主消息（errmsg 或 errmsg_internal）” | `elog.h` 第 93–107 行注释 |
| `ERROR` 用于用户错误并中止事务；`FATAL` 终止进程；`PANIC` 拉垮其他后端 | 级别语义严格区分 | `elog.h` 第 46–50 行注释 |
| 捕获 `ERROR` 必须使用 `PG_TRY/PATCH/RE_THROW`，不可用 C++/goto 模拟 | 文档强调“recovery section 中若有新错误会正确传播，但需简单” | `elog.h` 第 254–312 行注释 |
| `PG_CATCH` 中修改的局部变量须声明 `volatile` | POSIX 合规性要求，编译器优化会破坏跳转后的值 | `elog.h` 第 305–311 行注释 |
| `ereport(FATAL)` 不会被 `PG_TRY` 捕获，直接经 `proc_exit` 退出 | 因此不能在 recovery 段中释放非进程本地资源 | `elog.h` 第 298–303 行注释 |
| 错误处理代码必须能在 aborted transaction 中安全执行 | 注释指出 syscache 查找等操作不安全 | `elog.c` 第 6–10 行注释 |
| 新增 SQLSTATE 码应添加到 `errcodes.txt` 并由工具生成 `errcodes.h` | 文件头注明“autogenerated from errcodes.txt, do not edit” | `errcodes.h` 第 1–2 行 |
| 后台工作者循环统一用 `PG_TRY` 包裹，出错后 `EmitErrorReport` + `FlushErrorState` 继续 | 观察 autovacuum/bgwriter/checkpointer/walwriter 一致模式 | 多处源码实现 |
| 存储层 I/O 错误（如 EIO）应 `elog(PANIC, ...)` | 注释明确要求“不能忽略 EIO，否则恢复不可恢复” | `heapam.c` 第 6402 行附近注释 |

该体系在 MiniPostgreSQL 中被完整保留，所有后端子系统（access、catalog、commands、executor、storage、postmaster、tcop）均遵循同一套 `ereport` + `PG_TRY` 约定，确保错误从底层存储到协议层的统一传播与呈现。
